# 어디에 열까

공공데이터를 겹쳐서 보는 소규모 창업 입지 리포트. 클라우드컴퓨팅 실습 팀 프로젝트.

`index.html`은 5주차 아이디어 공유 때 쓴 발표 자료입니다(그때 계획 그대로 두었고, 이후 바뀐 범위는 이 문서 6절과 `docs/presentation-notes.md` 8절에 있습니다).

지금 상태는 다음 문서를 보면 됩니다.

- 서비스 구성·배포 주소: `docs/architecture.md`
- DB 테이블: `docs/db-tables.md`
- 데이터 규칙: `docs/common-rules.md`
- 발표 근거(출처, 처리 근거, 한계): `docs/presentation-notes.md`

## 1. 과제 요건

8주차 발표까지 만들어야 하는 것입니다. 페이지의 모든 결정이 여기서 나왔습니다.

**개발 환경** (수업에서 지정)

| 구분 | 방식 | 플랫폼 |
|---|---|---|
| 프론트엔드 | React 기본, HTML·CSS·JS 직접 구현도 가능 | Vercel |
| 백엔드 | FastAPI | Render |
| 데이터베이스 | PostgreSQL | Supabase |
| 소스 코드 | 저장소 관리 | GitHub |

**데이터 요건**

- 외부 API로 오픈 데이터·텍스트 데이터를 활용하거나, 크롤링으로 비정형 데이터를 수집한다
- 출처를 명시한다 — 외부 API·오픈 데이터의 명칭, 제공 기관, 출처 URL. 크롤링이면 대상 사이트와 수집 항목
- **수집한 데이터를 설명하고 기초적인 사항을 분석·정리해 보여주는 페이지를 반드시 포함한다**

**발표에서 설명할 6가지**

1. 서비스 아키텍처 — 프론트엔드·백엔드·DB·외부 API의 구성, 연결 관계, 데이터 흐름
2. 사용 데이터 및 출처
3. 데이터 활용 기획 시나리오 — 어떤 사용자의 문제를 해결하며 데이터를 어떻게 활용할 것인지
4. 비즈니스 모델 — 대상 고객, 제공 가치, 수익 창출 또는 지속 가능한 운영 방안
5. 주요 페이지 및 기능
6. 데이터 분석·정리 결과

**발표 자료에 포함할 것**

- 주소 3개 — GitHub 저장소, 서비스 웹 주소, Swagger UI
- 문서 2개 — API 설명 문서(기능, 요청 방식, 입력값, 응답 형식), DB 테이블 문서(테이블 구성, 주요 컬럼, 기본키·외래키, 테이블 간 관계)

**평가**

- 에이전트 코딩을 활용해도 된다
- **프론트엔드는 평가에서 제외된다.** 발표는 기획과 구조, 데이터 활용 방식, 주요 기능을 설명한다

화면을 다듬는 데 시간을 쓸 이유가 없다는 뜻입니다. 기획·데이터·아키텍처에 무게를 둡니다.

## 2. 아이디어

**문제.** 가게 자리는 아직 감과 발품으로 정합니다. 사람이 얼마나 지나다니는지, 같은 업종이 몇 개나 있는지, 그 자리가 얼마나 자주 바뀌는지 아무도 정리해주지 않습니다. 필요한 숫자는 이미 공개돼 있지만 여러 곳에 흩어져 있고 기준 코드도 다릅니다. 합쳐주는 상권분석 리포트는 유료 컨설팅 영역이라 1인 창업자에게는 문턱이 높습니다.

**사용자.** 1~2인 규모로 창업을 준비하는 사람. 계약서에 도장 찍기 전에 후보지 서너 곳을 스스로 걸러내고 싶은 단계에 있습니다.

**하려는 것.** 흩어진 공공데이터를 행정동 코드와 주소를 기준으로 하나의 DB에 모으고, 입지 판단에 필요한 네 축을 한 화면에 나란히 놓습니다.

**관점.** 점수 하나로 줄 세우지 않습니다. 어떤 자리가 좋은지는 업종과 사람마다 다릅니다. 우리가 하는 일은 비교 가능한 형태로 만들어 주는 것까지입니다. — 이 원칙이 아래 지표 설계 전체를 지배합니다.

## 3. 네 축과 지표

각 지표를 왜 그 형태로 정의했는지가 중요합니다. 발표에서 질문이 들어올 지점이기도 합니다.

### 경쟁 — 같은 업종이 이미 얼마나 있나

```
업종별 점포 수 ÷ 행정동 면적
```

점포 수만 세면 큰 동네가 항상 불리합니다. 면적으로 나눠야 밀도가 됩니다.

### 안정성 — 이 동네에서 이 업종이 버티나

```
3년 생존율 = 3~8년 전에 개업한 업소 중 3년 이상 영업했거나 아직 영업 중인 비율
교체율     = 최근 1년 폐업 수 ÷ 1년 전 영업 중 업소 수
신규율     = 최근 1년 신규 인허가 수 ÷ 1년 전 영업 중 업소 수
```

생존기간 평균을 쓰지 않은 이유가 있습니다. 폐업한 업소만 모아 평균을 내면 아직 영업 중인 가게가 계산에서 빠져 실제보다 짧게 나옵니다. 개업 시점이 충분히 지난 업소만 모아 비율로 계산하면 그 왜곡을 피할 수 있습니다.

교체율은 높다고 곧 나쁜 동네가 아닙니다. 임대료를 못 버텨 나가는 곳일 수도, 수요가 많아 계속 새로 들어오는 곳일 수도 있습니다. 그래서 **신규율을 항상 나란히 보여줍니다.** 둘 다 높으면 활발한 상권, 폐업만 높으면 빠지는 상권입니다.

### 자리 — 이 자리는 얼마나 자주 바뀌었나

```
같은 지번에 새로 들어온 가게 수 (최근 10년, 주인만 바뀐 같은 가게는 하나로 셈)
각 가게의 영업 기간 = 폐업일 - 인허가일
```

동네가 괜찮아도 유독 안 되는 자리가 있습니다. 인허가 데이터에 개업일과 폐업일이 남아 있어 자리 단위로 복원할 수 있습니다. 권리금을 부르는 쪽에 되물을 근거가 됩니다.

### 수요 — 사람이 얼마나, 언제 지나가나

```
행정동 안 지하철역의 하루 평균 승하차 (평일·주말)
시간대 지표: 아침 07~09시 하차·승차, 저녁 18~20시 하차, 심야 22~23시 승차
```

총량보다 시간대 분포가 중요합니다. 점심에만 몰리는 동네와 저녁까지 남는 동네는 같은 인구수라도 다른 자리입니다.

## 5. 데이터 모델

실제 DB 구성은 `docs/db-tables.md`에 있습니다. 모든 지표 표가 행정동 코드(`adm_cd`) 하나로 이어지고, 자리 축은 `site`(지번 하나) → `site_store`(그 지번에 있었던 가게들)로 나뉩니다.

5주차에 구상한 "주소를 별도 테이블로 빼서 여러 업소가 하나의 주소를 가리킨다"는 생각은 `site` 표로 이어졌습니다. 같은 자리에 들어왔다 나간 가게들이 같은 `site`를 가리켜 자리 이력이 나옵니다.

## 6. 내부 결정 사항

발표 페이지에는 넣지 않기로 한 것들입니다. 작업할 때는 따릅니다.

**다루는 범위**

- **서울 전체, 카페·제과점·한식 3개 업종**입니다. 처음엔 한 구로 시작하려 했으나 2026-10-12에 서울 전체로 넓혔습니다. 업종마다 생존 양상이 달라 섞으면 지표 의미가 흐려져 업종은 3개로 나눕니다.
- **기준일은 2026-09-30**입니다. 데이터를 세는 규칙(팝업 제외, 폐업일 없는 업소 등)은 `docs/common-rules.md`를 따릅니다.
- 종합 입지 점수는 만들지 않습니다. 네 축을 하나로 합치려면 가중치를 정해야 하는데 근거를 댈 수 없습니다.
- 같은 건물의 호수는 구분하지 않습니다. 주소만으로 2층 A호와 B호를 나눌 수 없습니다. 자리 이력은 지번·건물 단위로 집계하고 화면에 그 범위를 명시합니다.
- 생활인구와 후보 주소 반경 내 동종 업소 수는 다루지 않습니다(시간 부족). 수요는 지하철 승하차로, 경쟁은 행정동 밀도로 봅니다.
- 개별 권리금 시세는 다루지 않습니다. 공개 통계가 상권 평균까지입니다.

**붙이는 순서**

1. 인허가 데이터 — 네 축 중 경쟁·안정성·자리 셋이 이것 하나로 나옵니다. 주소 정규화와 스키마를 여기서 확정하고, 화면과 데이터 페이지까지 배포해 동작시킵니다.
2. 지하철 승하차 — 수요 축. 역을 행정동에 연결하면 기존 화면에 열 하나가 붙는 구조입니다.
3. (하지 않음) 생활인구, 임대동향

단계마다 배포된 상태를 유지합니다. 뒤가 늦어져도 앞은 그대로 동작합니다.

**주소 정규화 방침**

퍼지 매칭을 하지 않습니다. 지번이 정확히 일치할 때만 같은 자리로 묶습니다. 표기만 맞춥니다("106-0" = "106", "256-0257" = "256-257", `jari/common.py`의 `jibun_key()`). 못 잡는 경우는 화면에 한계로 표시합니다.

## 7. 리스크

- **주소 정규화 품질이 자리 축의 정확도를 결정합니다.** 지번과 도로명이 섞여 있고 표기가 제각각이라, 같은 자리인데 다른 주소로 잡히면 회전 횟수가 실제보다 적게 나옵니다. 발표에서 질문받을 가능성이 높은 지점입니다.
- **좌표도 주소도 못 찾은 가게.** 기준일 영업 중 세 업종 71,880곳 중 467곳은 행정동을 붙이지 못해 서울 합계에만 들어갑니다(원인은 `docs/presentation-notes.md` 7절).
- **폐업 신고 없이 닫은 가게.** 인허가 데이터에는 영업 중으로 남습니다(`jari/README.md`).

```
index.html    5주차 아이디어 공유 발표 자료 (프레임워크 없는 HTML 한 장)
README.md     이 문서
competition/  경쟁 축: 인허가 정제, 공용 파일(permits_base.csv) 생성, 행정동 기준표
stability/    안정성 축: 교체율·신규율·3년 생존율, 팝업 판정(temp_rule.py)
jari/         자리 축: 자리 지표, 주소로 행정동 채우기
demand/       수요 축: 지하철 역별 승하차, 역 → 행정동
backend/      API 서버 (FastAPI), DB 적재 스크립트 (load_data.py, load_sites.py)
frontend-html/ 서비스 화면 (HTML·CSS·JS)
batch/        월간 데이터 갱신 (매월 1일, GitHub Actions)
docs/         공통 데이터 규칙, 서비스 아키텍처, DB 테이블, 발표 근거
```

원본·중간 데이터(`data/`)와 인증키(`.env`)는 저장소에 올리지 않습니다.

배포 구성과 주소는 `docs/architecture.md`에 있습니다.

### 5주차 페이지 고치기

`index.html` 하나만 열면 됩니다. 빌드 과정이 없고 브라우저로 파일을 직접 열어 확인할 수 있습니다. 내부 구조는 이렇습니다.

- 파일 맨 위 `<style>` 안에 `:root` 로 색·간격 토큰이 정의돼 있습니다. 색을 바꾸려면 여기만 고칩니다. 다크 모드 값이 따로 있으니 둘 다 손봐야 합니다.
- 본문은 `<section>` 하나가 한 항목입니다. 왼쪽 `.rail` 에 번호와 라벨, 오른쪽에 내용이 들어가는 2열 격자입니다.
- 번호는 손으로 매겨져 있습니다. 섹션을 추가하거나 지우면 뒤 번호를 같이 고쳐야 합니다.
