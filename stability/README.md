# 안정성 축 데이터 — "이 동네에서 이 업종이 버티나"

서울 전체 427개 행정동 × 업종 대분류 12개(+전체)에 대해 3년 생존율, 교체율, 신규율을 계산해 CSV로 냅니다.

## 실행

```bash
cd stability
pip install -r requirements.txt

# 0) 인증키 설정 — 저장소에 커밋되지 않는 .env 파일에 넣는다
cp .env.example .env                      # 그다음 .env 를 열어 SEOUL_API_KEY= 뒤에 키 입력
python collect.py --check                 # 키·접속 확인 (서비스당 1건만 요청)

# 1) 수집
python collect.py                         # raw/ 에 일반·휴게·제과점 약 70만 건, 수 분 소요. 끊기면 다시 실행하면 이어받음
# (이미 두 개를 받았다면 제과점만: python collect.py --only LOCALDATA_072218)

# 2) 집계 — 행정동 경계는 처음 실행할 때 자동 다운로드
python build_stability.py                 # 기준일 = 오늘
python build_stability.py --base-date 2026-09-30 --min-n 20
```

## 인증키 관리

- 키는 `SEOUL_API_KEY` 하나만 씁니다. 읽는 순서: `--key` 인자 → 환경변수 → `stability/.env` → 저장소 루트 `.env`
- `.env`는 `.gitignore`로 막혀 있고 `.env.example`(빈 값)만 커밋됩니다. **키를 코드·README·이슈·PR 코멘트·단톡방에 붙여 넣지 마세요.**
- 화면과 에러 메시지에는 키가 `abcd********5678`처럼 가려져 찍힙니다.
- Render 배포 시: 서비스 → Environment → `SEOUL_API_KEY` 추가 (대시보드 값이 `.env`보다 우선)
- 키가 노출됐다면 열린데이터광장 마이페이지에서 재발급하고 이전 키는 폐기하세요.

## 교차검증 (API 수집본 vs 내려받은 CSV)

열린데이터광장·공공데이터포털에서 내려받은 CSV(한글 컬럼명, cp949, `20200101` 형식 날짜)도 그대로 넣을 수 있습니다. 같은 기준일로 두 번 돌린 뒤 비교합니다.

```bash
python build_stability.py --base-date 2026-10-15 --out out_api
python build_stability.py --base-date 2026-10-15 --out out_dl \
    --restaurant-file <다운로드_일반음식점.csv> --cafe-file <다운로드_휴게음식점.csv>
python compare_sources.py out_api out_dl --competition ../competition/competition_by_dong.csv
```

`out_api/compare_report.md`에 세 가지가 나옵니다.
1. 업소 단위: 한쪽에만 있는 관리번호, 공통 업소의 상태·인허가일·폐업일·행정동 불일치 건수와 예시
2. 지표 단위: 업종별 영업 중 업소 수·교체율·생존율 최대 차이, 차이가 큰 행정동
3. 경쟁 축과 비교: 카페·한식 영업 중 점포 수의 행정동별 상관 (업종 정의가 조금 달라 값이 같진 않고 방향만 봄)

갱신 시점이 며칠 다르면 최근 개·폐업 몇 건 차이는 정상입니다. 지번주소가 서울이 아닌 행(전국 파일)은 자동으로 제외됩니다.

### 다른 축과 연결

- `stability_by_dong.csv`의 `adm_cd`(10자리)는 `competition/dong_area.csv`·`competition_by_dong.csv`의 `adm_cd`와 같습니다. 행정동 경계도 같은 파일(admdongkor 2026.07.01)을 씁니다.
- `행정동코드`(8자리)는 `dong_area.csv`의 `adm_cd8`과 같고, 서울 생활인구와 바로 조인됩니다.
- 업종은 12개 대분류로 경쟁 축(카페·제과점·한식)보다 세분돼 있습니다. 경쟁 축의 '카페'·'한식'은 같은 이름으로, '제과점'은 '베이커리·디저트'로 찾으면 됩니다. 두 축 모두 제과점영업 데이터셋을 씁니다(여기선 휴게음식점의 과자점·아이스크림도 함께 묶음).
- `stores_clean.csv`의 `임시영업` 열로 팝업·행사 인허가를 걸러 쓸 수 있습니다. **자리 축(같은 주소 회전율)은 이 필터가 특히 중요합니다.** 백화점 한 지번에 3년간 1,000건 넘는 팝업 인허가가 있습니다.

## 설계 결정 (발표 Q&A 대비)

- **팝업·행사 인허가 제외** — 실데이터에서 백화점·복합몰 지번 한 곳에 3년간 600~1,000건의 인허가가 있었고 폐업분의 영업기간 중앙값이 10~20일이었습니다(신세계 강남·코엑스·더현대 서울 등). 이대로면 삼성1동·반포4동이 '서울에서 가장 빨리 망하는 동'으로 나옵니다. ① 사업장명에 '한시적·임시·팝업·행사'가 있거나 ② 최근 3년 인허가 30건 이상·절반 이상이 90일 내 폐업한 건물에서 90일 내 폐업한 업소를 지표에서 뺍니다. 같은 건물이라도 오래 영업한 입점 매장은 남깁니다. `--keep-temporary`로 빼기 전 결과도 낼 수 있습니다.
- **표본 부족 시 자치구 값 대체** — 업종을 12개로 나누면 분식·중식 등은 동별 업소가 적어 비율이 흔들립니다. 원래 비율은 비워 두고, 화면용 `표시_*` 열에는 같은 구 값을 넣어 '구 평균'임을 표시합니다.

- **생존율을 '평균 영업기간'이 아니라 비율로 계산** — 폐업 업소만 평균 내면 영업 중인 가게가 빠져 짧게 나옵니다. 개업 후 3년이 충분히 지난 코호트만 봅니다.
- **코호트를 최근 5년(8~3년 전 개업)으로 제한** — 오래된 개업분까지 넣으면 '살아남은 노포'만 남아 생존율이 부풀려집니다.
- **교체율 분모는 1년 전 시점의 영업 업소 수** — 기간 시작 시점 기준이라 연중 신규 개업이 분모를 흔들지 않습니다.
- **영업상태**: 휴업은 영업 중으로, 취소·말소·정지 같은 행정처분은 창업·폐업 흐름과 성격이 달라 제외. 폐업인데 폐업일이 없는 건은 시점 지표에서만 빠집니다.
- **업종 제외**: 편의점, 출장·이동조리, 푸드트럭, 역 구내·백화점 등 소규모 창업 입지와 무관한 업태. 규칙은 `category_map.csv`에서 고칠 수 있습니다(위에서부터 처음 맞는 키워드 적용).
- **좌표계**: 데이터 설명이 데이터셋마다 다르게 적혀 있어(EPSG:5174 / GRS80) 두 후보로 모두 매핑한 뒤 '주소상 자치구 = 경계상 자치구' 일치율이 높은 쪽을 자동 채택합니다. 결과는 `quality_report.json`의 `좌표계_검증`에 남습니다. 실제 샘플 5건은 EPSG:5174에서 모두 주소와 같은 행정동에 들어갔습니다.
- **행정동은 좌표로 매핑** — 인허가 데이터의 주소 속 동 이름은 법정동이라 행정동 코드와 1:1이 아닙니다.

## 한계

- **생존율이 공식 통계보다 높게 나옵니다**(서울 전체 약 60%, 통계청 음식점업 3년 생존율은 40%대). 인허가는 영업자 지위승계(주인 변경) 시 같은 관리번호로 이어지는 경우가 있어 '가게(자리)의 생존'에 가깝고 '사업자의 생존'보다 길게 잡힙니다.
- 좌표 누락은 개업연도·영업상태와 무관하게 7~9%로 고르게 분포해(diagnose.py 확인), 지표를 한쪽으로 치우치게 하지는 않습니다.

- 같은 자리에서 주인만 바뀌어 폐업 후 재인허가한 경우도 폐업 + 신규로 잡힙니다. 창업자 입장에선 실제 교체이므로 그대로 둡니다.
- 좌표가 없는 업소는 행정동 지표에서 빠집니다(비율은 `quality_report.json`).
- 인허가 기준이라 신고만 하고 실제로 열지 않은 업소가 섞일 수 있습니다. 서울시 상권분석서비스(점포-행정동)의 개·폐업률과 비교해 방향이 맞는지 검증용으로 볼 수 있습니다.
